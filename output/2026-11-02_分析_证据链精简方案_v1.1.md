## 0. 结论先行

精简后的流程是 **3 段**（取数落盘 → 脚本计算 + 报告内嵌引用 → 出报告 + 反方）。旧流程 5 段里被砍掉的是「独立台账」与「全量门禁/独立校验」两层，**不是溯源本身**。

**一句话**：Claude Research 把证据**焊死在报告里**，我们把证据**做成了报告之外的第二套系统**。过度设计的根在这一步，不在文件多。

## 1. 最新的流程是什么样的

### 1.1 精简后（目标态）

| 段 | 动作 | 门禁 | 产物 |
|---|---|---|---|
| **① 取数即落盘** | 外部取数 → 原始返回按次写文件（JSON / 去标签正文 + URL + `fetched_at`） | 原始文件不可改 | `fund_flow.json`、12 个行业 JSON、文本快照 |
| **② 脚本计算 + 内联引用** | 脚本读取 → 计算 → **生成报告时把来源锚点写进同一份 HTML/MD** | 结论由脚本生成，禁止手写数字 | 自带来源块的报告、可复算脚本、`analysis_v2.json` |
| **③ 出报告 + 反方** | 反方 ≥5、失效阈值、口径块；**推 Lark Doc（单向）** | 判断质量不过自动 | 报告定稿（Lark Doc）、`views:` 登记、memory 日志 |

**回灌闭环保留**：每轮把踩到的坑写回 `SKILL.md` / `data-recipes.md` / `CHANGELOG.md`。这是「模板是用出来的」约定，成本极低。

## 3. 为什么状态机「过时」

### 3.1 先纠一个前提

我上一轮**没有**说状态机过时。我说的是：**「状态机作为准确性保障」是错位的** —— 它属于**复用层**，我却把它和 manifest、hash、校验一起算进了「保证数据正确」的账里。老板 11-01 那句「问题不在于硬追溯，而是准确的呈现你的发现和结论」戳的就是这个混同。

准确表述是：**状态机没过时，但它的「形态」和「每轮必付的成本」过时了。**

### 3.2 三个意义上的判定

| 层面 | 判定 | 依据 |
|---|---|---|
| 作为**准确性保障** | **过时 / 错位** | Claude Research 用 inline citation + end-state evaluation 就够，它没有任何状态机 |
| 作为**跨会话复用** | **未过时** | 本库立身之本是「资产可沉淀 / 复用 / 迁移 / 审计」，一次性任务天然无记忆 |
| 作为**当前具体形态** | **过重** | 六段（node / focus / claims / monitors / queue / datasets）手写 yaml + 每轮手工回写，是「前 LLM 时代对抗模型失忆」的设计；现在有长上下文、`conversation_search`、`.workbuddy/memory/` 按日日志 |

### 3.3 最硬的一条：收益从未被兑现，成本却每轮必付

项目记忆里已有两个未闭环事实：

- 度量「结论命中率」衡量的是 **reused（被复用）而非 verified（被验证）** —— 已知缺陷：错误但高频引用的 claim 会拿满分；
- **报告质量 rubric（评分卡）缺失**，被标为「阻断性」。

也就是说：状态机宣称的收益（让结论可复用、可审计）**从来没有被验证过**，但「开场 `load_context`、收尾回写 `research-state.yaml`」是每轮固定成本。这不是"过时"，是**投入产出没闭环**。

### 3.4 处置（已批准降级）

> **✅ 已批准（P06 试点，2026-11-02 晚）**：状态机自本日起降级为**可选复用层**，非每轮回写门禁。
> P06 `research-state.yaml` 顶部已加标记；后续重跑只按需更新，不强制六段全写。准确性保障改由
> 「报告内联引用 + 口径块 + 反方≥5」承担。

**降级为可选，不删除**：

- 一次性任务：不建 `Pxx/`、不写状态机，报告自带结论 + 反方 + 口径即可；
- 月频重跑 / 跨会话续做 / 多人协作：才启用项目层；
- 真要证明它值这个成本，先补 **报告质量 rubric**，再用 metrics 第二轨验证「复用是否真的提升了结论质量」。在那之前，别把它当门禁。

## 4. 数据源和报告一起输出，如何保证溯源？是不需要了吗？

### 4.1 不是不需要，是换位置

**不需要的是「溯源台账」，不是「溯源能力」。** 把引用从报告里抽出来独立成 manifest，反而制造了「引用与输出会漂移」的新问题 —— 而 Anthropic 的 `CitationAgent` 恰恰是在最后一步把引用**焊死**到报告上：处理文档与报告、定位每条 claim 的具体引用位置、确保归因。

### 4.2 「一起输出」≠ 把原始 JSON 全文贴进报告

这条必须说死，否则会从「台账过重」滑向「报告变成数据转储」，同样毁掉阅读性（老板 11-01 第 4 条反馈）。正确形态是**三层内嵌**：

| 层 | 内容 | 放哪 |
|---|---|---|
| **① 数字锚点** | 每个关键数字旁标 `来源文件 + 原文可检索片段（短引文） + 抓取时间` | 报告正文脚注 / 悬停 |
| **② 口径块** | 单位、基准日、缺月处理、代理指标定义、known caveat | 报告顶部 |
| **③ 来源索引** | 13 个原始返回路径 + `fetched_at`（hash 可选） | 报告附录 |

原始返回**仍独立落盘**，不进报告正文 —— 它服务于「复算」，不服务于「阅读」。

### 4.3 溯源能力对照

| 能力 | 台账模式 | 内嵌模式 | 判定 |
|---|---|---|---|
| 数字 → 原文 | 靠 `evidence:` 指向整文件 + 校验脚本 | 报告内短引文 + 路径，一眼可见 | **更强**（引用与结论同处，不会漂移） |
| 复算 | 脚本 + 输入落盘 | 同样（这层没变） | 不变 |
| 反驳 | 反方 ≥5 + 失效阈值 | 同样 | 不变 |
| 谁在何时改了哪个文件 | `sha256` / `mtime` / `--check` | 无 | **单人自用不需要**；多人协作才补 |
| 跨会话「上次到过哪」 | 状态机 | memory 日志 + 报告本身 | 够用 |

### 4.4 诚实边界

内联引用**不是万无一失**：模型完全可能给出一个**真实存在但不支持该结论**的来源。Anthropic 的 judge 五维里单列「引用准确性（do the cited sources match the claims?）」正是为此。所以保留两道人肉闸：**反方 ≥5** 与 **口径块**。这也说明为什么「准确呈现」比「硬追溯」更该投入 —— 前者防的是语义错配，后者只防文件被改。

### 4.5 交付载体：Lark Doc 为主，Sheet 入 reference（采纳 4 点反馈 ②）

"数据源和报告一起输出"的**载体形态**现在定下来（即把 §4.2 三层内嵌**物化到 Lark Doc**）：

- **主载体 = Lark Doc**：人读的这一份就是交付物。结构按 §4.2 三层展开 ——
  ① 顶部**口径块**（单位 / 基准日 / 缺月 / 代理指标定义 / caveat）；
  ② 正文**内联引用**（每个关键数字旁标 `来源文件 + 短引文 + 抓取时间`）；
  ③ 末尾 **reference 段**：来源索引（原始返回路径 + `fetched_at`）。
- **Lark Sheet 退为可选附件**：只有当存在**复杂计算**（多表联动、可复算矩阵）时，才额外生成 Sheet，**放在 Lark Doc 末尾的 reference 段里作为链接**，不再独立成 7-tab 主交付。Sheet 仍 local→lark 单向、本地 SSOT。
- **原始返回不入 Doc 正文**：它服务于"复算"，放在本地 `artifacts/` + reference 索引即可。

这与 Claude Research「引用焊死在输出里」一致，且把"台账那套第二系统"彻底收进报告自身。

## 5. 复杂的任务也使用这种模式吗？

**基线永远用，加料按需。** 内嵌引用成本近零，任何任务都该做；复杂任务额外加的东西，和「台账」无关。

| 任务特征 | 额外加什么 | 不加什么 |
|---|---|---|
| 多源、breadth-first | **≥2 路真正独立源**交叉验证；并行检索 | 不把 3 篇同源转载当 2 源（P06 实际栽在这：证券时报一家、均引 Wind，行业层 +39 亿与概念层 +40 亿出自同一句） |
| 需要跨会话续做 / 月频重跑 | 项目层 + 状态机 + lark 单向视图 | 不加 hash / stage 台账 |
| 判断类结论（四象限、α 判定） | `decision_log`：判定依据 + **被否决的备选项**；标 `kind: judgment` | 不假装可复算 |
| 结论要对外 / 入决策 | **五维 rubric**：事实准确性 / 引用准确性 / 完整性 / 来源质量 / 工具效率 | 不用「看图表顺眼」代替评分 |
| 一次性、答案唯一 | 直接跑 3 段 + 轻量 Lark Doc | 不建项目层、不跑全量门禁 |

两个约束：

1. **Anthropic 的 15× token 成本**是真实代价。多 agent / 多源并行只在任务价值足够高时才划算，别为「近一周 Top10」这种问题开 10 个 subagent。
2. 本库**报告质量 rubric 仍缺失**（记忆中标为阻断性）。但现已明确其**时机**（见 §8 Q3）：规则前置为自检清单、评分后置，先出 v1 草稿。

## 8. 针对 4 点反馈的答复（2026-11-02 晚）

**Q1 · 一次性问题为什么不推 Lark？**
v1 §1.3 写"否"是错的、且自相矛盾。逻辑反过来才对：**正因为没有 Lark 文档，后续才无法轻度引用**——
所以一次性问题也该产出一份**轻量 Lark Doc**（仅 findings + 内联引用 + 口径块，不建 7-tab Sheet）。
这样未来报告可以"详见 P06 Lark Doc §X"做轻引用，而不是重新推导。已修正 §1.3。

**Q2 · 数据源 + 报告一起输出的交付形态**
定为 **Lark Doc 为主载体**：① 顶部口径块 ② 正文内联引用 ③ 末尾 reference（来源索引）。
仅当有**复杂计算**时额外生成 Lark Sheet，**挂在 Doc 末尾 reference 段链接**，不再独立成主交付。
原始返回仍留本地 `artifacts/` + reference 索引，不进 Doc 正文。详见 §4.5。

**Q3 · rubric 在执行前还是执行后？**
**两阶段**：规则（"好"长什么样）**前置为自检清单**——执行前可见、执行中对照
（如"每个数字有内联引用""反方≥5""有口径块"）；**评分后置**——交付后按五维（事实/引用/完整/来源质量/工具效率）打分。
精简模式下不单列评分 pass，把规则焊进 method skill 当门禁（前/中合并）；后置评分仅用于对外/入决策的重型输出。

**Q4 · 按 P06 试点降级状态机**
**已批准并执行**：`research-state.yaml` 顶部加"可选复用层、非每轮回写门禁"标记；
后续重跑只按需更新，不强制六段全写。准确性保障改由报告内联引用 + 口径块 + 反方≥5 承担。

### 9.2 二级框架确认：在配置里，且先分类再调研
